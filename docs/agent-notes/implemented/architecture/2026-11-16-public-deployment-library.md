# Agent Note: 基于 SpiffWorkflow 的公共部署节点与交互运行入口

Status: implemented

## 问题

产品仓库需要拥有自己的部署策略、安装材料和流程，公共库负责可复用操作及一致的执行体验。若安装流程集中在公共库中，产品变化就会牵动不应了解产品内部细节的仓库；若只提供命令执行函数，消费者又必须重复实现步骤组织、交互确认、结果传递和错误报告。

核心需求是根据前序步骤的真实结果决定后续动作。例如观察目标后决定安装、更新或复用，再把实际产物交给核查。提前展示完整差异不是所有节点的前提。公共能力必须能够在控制端本地运行，依赖准备后无需外网、容器引擎或常驻服务。

本记录拥有公共包第一阶段的本地节点、审批与原生图职责决定。独立消费目录从本地 wheel 安装后，用一个编排脚本运行本地文件安装流程。SSH、pyinfra、OpenTofu、下游设计 skill 和 PyPI 仍未实现，后续范围不随本记录的第一阶段生命周期变为已实现。

## 决定

使用 SpiffWorkflow 管理流程实例、节点生命周期、连接和条件路由；xxautoenv 提供基础节点与统一终端入口。消费者直接组合节点并使用 SpiffWorkflow 的条件节点，不引入第二套流程 DSL、插件中心、可替换引擎接口或独立调度状态。

| 所有者 | 职责 |
|---|---|
| 公共包 | 节点适配、基础操作、输入交互、动作展示与确认、输出和详细诊断、核查汇总 |
| SpiffWorkflow | 节点可执行性、路径选择、流程推进及原生执行状态 |
| 消费仓库 | 产品节点、支持平台、部署策略、输入输出连接、条件分支及产品验收规则 |
| 消费脚本 | 构造流程并调用公共运行入口，将运行结论映射到进程退出码 |

公共包不注册产品目标或内置产品菜单。公开仓库只包含通用能力和简单示例；产品配方、实际部署配置及其历史由消费仓库拥有。产品接入不属于本仓库实施阶段。

### 第一阶段范围

交付函数节点、配置输入节点、本地命令节点、本地文件交付节点和核查节点，以及统一运行入口。提供一个完全本地的文件安装示例。构建 wheel，在独立消费目录验证安装和运行，不使用 editable 安装或源码路径绕过包边界。

SSH、pyinfra、OpenTofu 节点、下游设计 skill 和 PyPI 发布设施不进入第一阶段。后续范围由[路线图](../../../roadmap.md)维护。所需工具按节点需要提前准备，缺失时报错，公共运行入口不自动下载工具链。

### 运行环境与分发

首阶段使用 Python 3.12，以 Linux 与 macOS 为目标平台，采用普通纯 Python wheel 交付公共包，以 uv 管理开发依赖及锁文件。SpiffWorkflow 3.2.0 是探针验证基线，初始依赖固定到该版本；依赖更新需要验证节点适配，不预先承诺其他版本兼容。lxml 由 SpiffWorkflow 引入，其平台 wheel 应在准备阶段取得，不将编译器安装或源码构建安排到部署执行阶段。

实际实现与验证使用 macOS Python 3.12.16；Linux 文件、权限、替换及命令行为仍需补齐，尚未完成跨平台验收。公共包沿用仓库的 MIT 许可，SpiffWorkflow 作为外部依赖引用，不把上游实现复制成自有源码；依赖保留各自许可。

消费者维护 pyproject.toml、uv.lock 和 deploy.py。复杂产品可以拆分自己的节点模块，不强制单文件实现。第一阶段的消费依赖指向本地 wheel；依赖取得和环境同步属于准备阶段，执行脚本时不自动同步。安装与运行命令由已验证的[示例说明](../../../../example/local-file/README.md)维护；公共包尚未在 PyPI 发布。

离线运行不禁止产品明确声明的下载节点；若产品要求完整离线安装，则产品负责准备本地安装材料。公共运行时本身不得联网补齐引擎或工具。开发成熟后才核对 PyPI 名称、账号和认证，并另行安排正式发布。

## 节点与数据接口

以下概念表达公共契约，实际构造签名由 `src/xxautoenv/` 对应模块拥有。

| 概念 | 必需信息 | 作用 |
|---|---|---|
| 节点声明 | 唯一标识、名称、用途、阶段、输入绑定、输出名称、允许的动作范围 | 表达消费者可读的流程结构 |
| 节点准备 | 已解析输入和只读观察能力 | 生成本次绑定动作，或直接返回跳过结果 |
| 绑定动作 | 动作描述、具体对象及范围、是否变更、执行函数 | 展示和批准后执行同一份动作 |
| 节点产出 | 成功或跳过、值、摘要、跳过原因 | 供下游使用与终端展示 |
| 核查结论 | 通过、不通过或无法判定，及说明 | 独立于流程执行是否完成 |
| 运行结论 | 成功、失败、取消或中断，及步骤和核查报告 | 供入口汇总和退出 |

普通函数节点用于无变更计算和只读探测，函数返回值作为节点产出。会修改目标的函数必须显式提供准备与执行边界，不能在普通计算节点里隐式修改目标。框架不提供任意 Python 代码的沙箱；动作范围是节点作者声明并由适配检查的契约，不承诺识别被调用程序的一切副作用。

消费者声明每个输入来自哪个上游产出，或来自哪个显式常量。公共适配将这些绑定转换为 SpiffWorkflow 任务数据；业务函数只收到声明的参数，不直接读写整个任务字典。产出可以是普通 Python 对象，不要求为一次进程内运行增加序列化。

标识重复、未知输出引用、缺少必需输入和非法结果形状属于契约错误。构造时检查已知引用，执行时检查输入是否真正就绪，不以 None 代替缺失产出。第一阶段不实现通用静态类型推导、跨进程数据协议或持久化恢复。原生条件节点可以读取适配公布的数据名称；数据名称是接口的一部分，文档与示例应明确展示。

阶段内可预先连接备选路径，具体路径及动作参数在运行时根据前序结果确定。第一阶段不承诺任意运行时增删流程图、并发执行或循环调度；先用顺序推进和条件分支完成消费闭环。此限制不禁止某个节点根据输入生成本次具体操作。

跳过也必须返回有效产出。例如目标文件内容及权限已满足要求，交付节点返回现有目标位置和摘要，后续核查照常读取。未选中的分支不会执行，不生成虚假的业务失败，也不把它显示为目标已符合要求的跳过。

## 阶段、交互与动作确认

阶段计划采用“只读准备、真实状态展示、复用准备结果执行”顺序。运行器先让原生引擎按既有依赖顺序推进本阶段的只读函数探测，再为输入已就绪、路径已确定的动作做只读准备，结果保存在对应原生 task 的 internal_data。准备过程不得执行变更；实际执行复用同一个绑定动作或跳过结果，不重复准备。输入缺失和路径尚未确定时才延期准备，不能统一填入待定状态。函数节点的只读探测仍由原生引擎执行，不另建函数求值器、就绪队列或路由逻辑；输入交互、变更及最终核查在计划展示后正常执行。

计划接收只读准备快照：节点声明、准备状态和本次动作范围。状态区分已探测、就绪、无需变更、等待输入或依赖、分支未选择及核查无法判定；这些状态由原生任务、准备缓存和已确定路由推导，只供展示，不能反向驱动调度。普通准备失败在审批前停止并保留诊断，独立核查的普通准备异常延续既有无法判定及继续规则。晚就绪步骤在原生引擎推进到它时准备一次，计划中不能预报成功。只读探测步骤虽可能先完成，其结果仍须按实际顺序显示一次；准备失败、中断或取消时也不能丢失已完成步骤的结果。

保留引导、执行和收尾核查三个阶段。消费者为节点声明阶段并组织前后连接；阶段是流程的展示及处理语义，不是第二套任务容器。准备资料和配置在引导阶段完成，变更在执行阶段完成，最终核查保持只读。引导阶段若有明确写入动作，同样执行逐步审批。

第一阶段按引导、执行、收尾核查顺序组织流程，不允许通过连接从核查返回变更阶段。运行入口检查阶段倒退等无效组合；不引入通用分层调度器。阶段进入时显示名称与流程结构，尚未就绪的分支标记为待定，不展示假定的实际操作。

节点输入就绪后，准备函数可以观察状态、校验输入并生成绑定动作；不得执行下载、创建目录或修改文件等变更。配置输入节点可以在引导阶段请求用户输入，输入校验失败则在该输入处给出修正提示，不触发后续变更。

| 情况 | 展示与确认 |
|---|---|
| 只读探测、计算或核查 | 显示步骤用途，直接执行 |
| 配置输入 | 提示填写和校验，不额外询问是否允许提示 |
| 修改目标 | 展示具体动作、对象和范围，等待 y/N |
| 无需变更 | 显示跳过及理由，交付已有产出，不请求确认 |

阶段不重复请求整阶段批准。-y 只自动批准变更，仍显示动作，不代答缺失配置。非交互环境缺少必需输入或审批答案时明确失败，不无限等待；拒绝执行形成取消结果，不被误报为成功安装。

批准与执行绑定到同一个动作对象。不得批准后重新查询其他来源并偷偷替换本次动作；若必须改变已展示的操作，停止并说明原因。动作执行前可做必要的局部一致性检查，发现已观察前提失效则失败，不自动重新选择目标或扩大范围。这里不承诺跨命令事务、自动回滚或防止外部并发修改。

## 展示、错误与核查语义

仅阶段计划使用 `Rich.Table` 构造，依赖 `rich==15.0.0`，由 Rich 处理布局；表格保留 `#`、`说明`、`Allowed actions`、`Status`，不单列步骤名称。说明在计划中集中展示，过程用阶段内编号定位，只显示必要动作明细、状态和结果，不重复输出用途。每个实际经过的步骤必须有一次明确结果；核查完成与业务通过与否合并显示，摘要不重复。阶段间使用 Rich `Console.rule` 分割线。全局开始提示和最终汇总逐行输出，不全量复述步骤说明。原始输出和异常原因链不做去重或过滤。

文案按生成者归属：`Allowed actions`、`Status` 两列的框架表头与占位值使用英文，状态直接使用 `PreparationStatus.value`；其他框架标签及自带节点生成的默认动作说明、摘要和诊断模板使用中文；消费者提供的说明、问题、默认值、自定义动作和结果摘要、校验错误原样显示。结构化节点名称和标识保留用于数据及诊断，不因 UI 去掉名称列而删除公开字段。动作说明与计划用途相同且没有新增内容时不复述，具体动作范围仍在批准前展示；批准提示不再次复制整段动作说明。路径、命令、动作标识、枚举值和外部原文保持原值。

每个实际经过的步骤按阶段内编号明确显示结果，成功也显示摘要。运行过程可显示等待输入、待确认和执行中；原生引擎切换阶段前先 flush 已有步骤回执，再根据原生事实发布本阶段未执行节点的处置；停止时尚未进入阶段的处置在全局部署结论前显示。终端只保存本次已发布的处置标识并在 begin 重置，完整 RunReport 保留全部步骤。未选择分支单独表示未选择，不与流程停止造成的未执行混淆，每条处置信息只显示一次。

框架执行状态、业务产出和运行结论承担不同职责。SpiffWorkflow 负责推进；节点产出记录完成了什么及其数据；运行结论归纳是否达到消费方的安装要求。报告保存结果证据，不反向成为另一套调度状态或步骤进度账本。

步骤报告使用不可变的 `StepReport(declaration: NodeDeclaration, result: NodeResult | None, diagnostic: Diagnostic | None, disposition: StepDisposition)`。`disposition` 在运行停止后根据原生任务与路径事实汇总：`EXECUTED` 表示步骤已实际经过，包括业务跳过、拒绝、失败或中断；`NOT_SELECTED` 表示已确定没有选中的分支；`NOT_EXECUTED` 表示已确定路径上尚未执行的步骤；`PENDING` 表示路由尚未确定。后三类不伪造业务 `NodeResult`；分类仅供报告与展示，不参与调度。

`Diagnostic(node_id: str, stage: Stage, error: BaseException, traceback: str)` 保存原始异常及完整原因链。`RunReport(status: RunStatus, steps: tuple[StepReport, ...], checks: tuple[CheckResult, ...])` 汇总本次原生 Workflow 的证据；每次调用运行入口都新建 Workflow 并重新绑定交互能力，不复用输入、结果或阶段状态。

普通步骤的准备或执行异常立即停止后续流程。保留原始异常原因链、失败阶段和节点、具体操作、命令、输出及已完成工作，不用通用错误消息替换底层原因。取消和中断分别报告，不捕获后伪装成正常完成。

不设计敏感信息隐藏机制：不增加脱敏、关键词识别、敏感字段标记、输出过滤或独立密码隐藏策略。节点决定输出哪些信息，运行时直接展示信息、命令输出和错误详情。输出展示不是要求把所有配置值或任意对象自动打印出来。

### 收尾核查

核查工厂在原生部署节点上设置内部 `_is_check` 标记，供图校验与结果汇总识别核查；`DeploymentNode` 的公开构造参数不增加核查开关。收尾核查由消费者定义多个独立的只读检查项。核查动作成功执行可返回“不通过”的业务结论；这不是框架执行错误。正常核查及已经报告的普通核查异常都可以让 SpiffWorkflow 节点正常完成，使后续独立核查继续执行。

| 核查情况 | 对外报告 | 后续处理 |
|---|---|---|
| 检查完成且满足要求 | 核查完成、通过 | 继续 |
| 检查完成但不满足要求 | 核查完成、未通过及原因 | 继续 |
| 普通准备或执行异常 | 核查异常、无法判定及完整错误 | 继续其他独立核查 |
| 流程契约错误 | 契约错误及定位 | 立即停止 |
| 用户中断 | 中断位置与已有核查结果 | 立即停止并保留中断语义 |

任一核查不通过或无法判定，整体失败。零变更或全部交付跳过时仍执行最终核查。普通执行步骤失败后不强行进入收尾核查，不附带自动修复、回滚或清理。第一阶段核查项不依赖其他核查结果，不建立“前置核查失败则自动跳过依赖核查”的新机制。

运行入口返回结构化运行结论，由 CLI 入口映射退出码：成功 0，失败 1，用户拒绝 2，键盘中断 130；其他显式退出保留其原因。

## 第一阶段基础节点

### 函数节点与配置输入

函数节点适配普通函数，解析声明输入，保存产出并生成结果摘要；业务函数不继承引擎类型。产品自定义变更节点使用同一个准备动作契约。配置输入节点支持默认值、必需性及消费者提供的校验函数；不建设通用配置文件格式或交互表单平台。

### 本地命令

命令节点显式声明 argv、工作目录、必要环境覆盖及是否修改目标。命令不默认经 Shell 拼接；确实需要 Shell 的消费者显式声明 Shell 命令。运行入口展示步骤、保留 stdout、stderr、退出码及失败命令。非零退出默认失败；消费者需要把某个退出码解释为正常业务判断时，应由其节点明确转换为结果。

不自动安装缺失的命令。交互命令需要明确继承终端；对于此类命令，不承诺重复捕获已经直接显示在终端的全部输出。命令中断必须结束本次等待并停止后续节点，不在后台遗留本次启动的受控子进程；范围限于本地命令适配可管理的进程，不承诺管理外部服务生命周期。

### 本地文件交付

输入是明确来源文件、目标路径和期望权限，输出是目标文件位置、摘要及必要元数据。观察目标内容和权限，均符合要求时返回跳过产出，否则准备本次写入动作并请求确认。

写入采用目标同目录临时文件后替换，避免直接截断已有目标；替换前核对来源材料没有改变。父目录不存在时，把创建目录明确包含在本次动作中。第一阶段不跟随目标符号链接，不覆盖非普通文件；冲突明确失败。不支持目录同步、任意权限所有者变更、历史备份或通用恢复机制。

### 核查节点

核查节点绑定只读函数或只读命令，产出结论与说明。普通异常由公共适配记录并转换为无法判定，契约错误与中断保持停止。内容摘要和权限核查分别作为简单示例的两个独立项目，避免使用一个通过结果代替全部核查。

## 源码模块与依赖方向

源码放在 src/xxautoenv，示例放在单数目录 example。第一阶段采用以下结构；文件承担独立职责，不为每个数据类型建立子包。

```text
src/xxautoenv/
├── __init__.py
├── contracts.py
├── node.py
```

| 模块 | 负责内容 | 不负责内容 |
|---|---|---|
| contracts.py | 阶段、输入绑定、准备动作、节点产出、核查结论、诊断及运行结论的数据结构 | 流程推进、工具调用和终端显示 |
| node.py | SpiffWorkflow 节点适配，输入解析、动作绑定、调用运行交互能力、产出保存及异常语义 | 产品分支、命令或文件操作细节 |
| workflow.py | 核对原生流程图中的节点标识、数据引用、阶段边界，提供展示所需的图信息 | 自行拓扑调度、复制流程图或保存另一套节点状态 |
| runner.py | 运行入口、CLI 参数、每次运行的交互上下文，调用 SpiffWorkflow，汇总结果及退出码 | 内置产品目标、工具专用协议 |
| terminal.py | 输入和确认、阶段与步骤显示、输出呈现、错误详情和最终报告 | 判断路径或产品成功条件 |
| operations/command.py | 本地子进程执行、工作目录与环境、stdout/stderr、退出与中断处理 | 节点状态、审批和流程阶段 |
| operations/files.py | 本地文件观察、摘要与权限、绑定材料的交付操作 | 是否允许覆盖的产品策略、终端审批 |
| nodes/function.py | 普通函数与自定义准备函数的节点构造 | 产品函数实现 |
| nodes/input.py | 配置提示、默认值和消费者校验函数接入 | 全局配置系统或配置持久化 |
| nodes/command.py | 将命令请求及执行结果接入节点契约 | 重复实现子进程管理 |
| nodes/file.py | 将文件观察、准备和交付接入审批与产出契约 | 选择产品安装目录和产品版本 |
| nodes/check.py | 只读核查适配、通过或不通过结果、普通异常转为无法判定 | 自动修复、重新部署或吞掉中断 |

contracts.py 不导入 SpiffWorkflow、节点、终端或工具集成。operations 仅依赖标准库及必要的公共数据类型，不反向导入 nodes、runner 或 terminal。node.py 依赖 contracts 和 SpiffWorkflow，通过每次运行注入的交互能力请求展示与确认，不直接构造终端。基础 nodes 依赖 node、contracts 和相应 operations；runner 组合 workflow、terminal 和原生引擎，不导入全部基础节点或可选集成。

消费者从 xxautoenv.runner 取得入口，从 xxautoenv.nodes 的具体模块取得节点，用 SpiffWorkflow 原生接口连接流程。__init__.py 仅提供包信息或少量稳定导出，不执行工具探测、不扫描插件、不导入全部节点。这里的内部职责分离不是可替换引擎抽象；node.py 和 workflow.py 可以直接使用 SpiffWorkflow 的实际类型。

### 后续工具模块

后续按实际实现增加以下目录，第一阶段不创建空文件、接口占位或未使用的依赖：

```text

src/xxautoenv/integrations/

│   ├── __init__.py
│   ├── adapter.py
│   └── nodes.py
└── opentofu/
    ├── __init__.py
    ├── adapter.py
    └── nodes.py
```

operations/ssh.py 拥有中性的连接参数、远端命令和传输能力；本地与远端请求可以复用 command.py 的进程执行，不为尚未实现的协议创建通用后端层。

integrations/pyinfra/adapter.py 拥有 pyinfra 调用、配方输入和报告解释，nodes.py 把这些能力接到相同的节点契约。消费者提供配方和主机选择；公共适配不维护产品包列表或服务配置。接入时再依据 pyinfra 实际接口决定使用 Python API 还是控制端子进程，不在目录设计中承诺未经验证的调用方式。

integrations/opentofu/adapter.py 拥有控制端 tofu 命令、计划文件及输出解析，nodes.py 提供相应计划和执行节点。消费方提供配置目录、变量和 backend 约定；资源 state 由 OpenTofu 管理，xxautoenv 不建立第二份资源状态。批准后执行同一份已展示的计划，计划和 state 不放入包安装目录。

两个工具集成都可依赖 contracts、node 和 operations，但不得互相导入。需要将基础设施输出交给主机配置时，由消费方连接节点产出，不让 pyinfra 适配直接查找 OpenTofu 状态。厂商 SDK 和产品插件不得成为公共包的无条件依赖。

新增 Python 依赖只归相应可选安装项；外部命令仍需消费环境提前具备。只使用本地节点的项目，导入和运行时不得要求安装 pyinfra、tofu 或 SSH 工具。第一阶段不声明空的可选安装项；后续集成同时验证基础包不带入工具依赖、显式选择集成后能够被消费者使用。

## 确定的本地示例

example/local-file 是独立消费者，不是根项目的 uv workspace 成员。pyproject.toml 声明 xxautoenv 依赖，uv.lock 锁定依赖，deploy.py 是唯一编排源码，assets/message.txt 提供固定普通文本。示例 README 只说明实际验证过的准备、执行、观察结果和常见失败处理，不重复公共包架构。

示例把 message.txt 安装到用户明确提供的目录，目标文件名固定为 message.txt，期望权限为 0644。目标目录是脚本参数；缺失时通过配置输入节点询问，无默认写入真实用户配置目录的行为。来源文件以 deploy.py 所在目录定位，不依赖调用者当前工作目录。

具体节点及连接如下：

| 阶段 | 节点 | 输入与产出 |
|---|---|---|
| 引导 | 获取目标目录 | 消费者参数或交互输入 → 规范化绝对路径 |
| 引导 | 确认来源材料 | 示例来源路径 → 固定内容摘要、权限要求和目标位置 |
| 执行 | 观察目标 | 目标位置 → 是否存在、普通文件类型、内容摘要与权限 |
| 执行 | 选择动作 | 来源要求和观察结果 → deliver 或 reuse |
| 执行 | 交付文件分支 | 明确来源及目标 → 请求逐步确认后交付，返回文件产出 |
| 执行 | 复用文件分支 | 已满足要求的观察结果 → 跳过及相同类型的文件产出 |
| 核查 | 内容核查 | 文件产出 → 重新读取内容并核对摘要，返回核查结论 |
| 核查 | 权限核查 | 文件产出 → 重新读取权限并核对 0644，返回核查结论 |

消费者用原生 ExclusiveChoice 选择 deliver 或 reuse，两个路径连接到同一组核查节点。复用节点经 `action_node` 返回跳过结果；交付节点仍自行做执行前一致性检查，消费方的早期观察不能替代这一检查。动作选择是示例策略，实际文件访问复用 operations/files.py，不在 deploy.py 复制文件交付实现。

成功路径始终执行两项独立核查。核查分别消费文件产出，不把第一项核查结论作为第二项的输入。首次运行写入文件，相同输入重跑跳过交付但继续核查；内容或权限改变时选择交付，拒绝后保留目标原状。目标是符号链接或其他非普通文件时，明确失败并停止，不能把异常观察结果默认解释为可覆盖。

本地命令节点不为凑齐示例而插入无关 Shell 命令；其消费契约由独立测试验证。示例保持文件安装这一个用途，失败注入、中断及契约错误场景属于测试，不增加故意损坏文件的产品选项。

### wheel 消费验证

构建产物放在根目录 dist，示例依赖准备阶段显式指向已构建 wheel。示例锁文件随该依赖更新。后续正式发布时再改成索引版本，不让示例执行时自行构建或下载公共库。

验收将 example/local-file 复制到仓库外的临时消费目录，把 wheel 放入该目录的本地依赖位置，再按该位置更新依赖来源和锁文件。清除源码路径影响，从实际 wheel 安装后运行 deploy.py；不能依靠仓库相对路径、父目录导入或开发虚拟环境偷带源码。依赖准备完成后阻止外网访问再执行示例。实际 uv 命令由示例 README 维护。

包构建只纳入 src/xxautoenv 和必要元数据，不把 example、测试、过程文件、构建缓存或部署产物打入 wheel。测试分别覆盖基础操作、节点适配、运行交互和独立 wheel 消费，不用一个集成示例代替每个公共接口的必要验证。

## 备选方案

**继续调整现有自有引擎。** 以明确结果引用和小型节点适配可以实现相同业务行为，本地对比也未发现正确性差异。但固定步骤列表需要在多个步骤重复分支条件，且自有执行生命周期仍需长期维护。原生条件节点更直接表达消费者拥有的路径选择，因此选择复用 SpiffWorkflow 内核；复用已有底层操作不等于迁入完整自有引擎。

**Dagger。** 模块复用与产物连接有价值，但引入容器运行环境和独立执行引擎，不满足轻量本地离线运行的要求。没有完成端到端运行验证，不以环境准备结果声称产品适配失败。

**Deployer 或 Mage。** 可以组织任务和调用既有工具，但结果驱动的步骤契约仍需自建，且为保留 Python 操作逻辑增加另一语言运行或发布环节。它们不是本设计的首选执行内核。

**直接包装整个产品安装步骤。** 将内部策略、闭包及共享状态保留，再在外层添加工作流节点，不能改善产品职责划分。基础操作和产品选择策略必须明确分开，公开包不接管产品分支。

## 验证与交付约束

1. wheel 仅包含公共包及必要元数据，不含产品私有内容、简单示例目录、过程文件或历史材料。独立消费目录从 wheel 安装，移除源码路径后仍可运行示例。
2. 示例由消费脚本组合节点，产品策略不进入公共包。根据真实目标状态走交付或复用路径，产物明确传给核查；重新运行重新观察目标，外部修改不能被执行缓存掩盖。
3. 变更逐步展示并确认，拒绝时目标不变；只读与跳过无需确认。批准期间更改其他选择变量不得替换已绑定动作。-y 不代答必需输入。
4. 每个实际执行步骤都有明确结果摘要。跳过仍提供可用产出，未选择分支、拒绝、异常与中断不混淆。输入缺失和非法节点契约能明确归责。
5. 普通执行失败停止后续流程，保留原始命令输出和异常原因链。真实终端输入及本地子进程中断需有定向验证，不只依靠替身回调。
6. 多项收尾核查中，不通过或普通异常后继续其他独立项目并整体失败；契约错误或中断停止。全部跳过变更时仍核查，框架完成不能误报部署成功。
7. 依赖准备后，示例运行不需要外网、Docker、独立引擎或常驻服务；测试禁止联网补依赖。macOS 已验证文件权限、替换和命令行为；Linux 尚未验证，不扩大成无实际承诺的平台矩阵。
8. 文档只给出实际验证过的消费、构建和测试命令。当前架构记录在实现后的 architecture.md，开发和测试命令各归其所有者；不添加重复全局规则的 AGENTS.md 或没有使用信息的 README。

### 选择证据与产品验证

选择阶段的本地探针使用 SpiffWorkflow 3.2.0、Python 3.12 和 lxml 6.1.3，确认原生分支、普通 Python 对象产出、跳过后继续核查及异常停止可运行。原生节点对比涵盖 8 个场景、两种引擎的 16 次执行，观察到业务路径、文件结果和错误定位一致。生命周期探针覆盖 11 个场景，包括绑定动作审批、拒绝、独立核查继续、契约错误与中断停止。

这些证据是设计可行性验证，不是本仓库发布产物的验收。探针使用本地临时文件、受控交互及模拟目标，没有验证完整终端界面、真实系统信号、远端 SSH、插件 ABI、pyinfra 或 OpenTofu。本阶段不迁入产品探针或以私有路径作为公开文档必需引用；发布产物的行为由本仓库自己的测试重新建立证据。

## 影响

SpiffWorkflow 任务数据以名称连接，薄适配需要提供明确输入检查，避免把字符串拼写错误延迟成无法定位的业务异常。该适配不能逐步演变为隐藏原生图的第二套 DSL。

展示结果包含业务结论、取消与中断，不能直接照搬全部框架状态。需要明确“核查完成但未通过”和“执行失败”，同时保持只有框架负责路径推进。普通核查错误转换不能吞掉契约错误、中断或原始诊断。

依赖准备仍有成本，lxml 使用平台 wheel。没有合适 wheel 的环境不在部署时自动构建；支持范围和交付验证必须一致。Python、退出码及文件节点遵循本记录的第一阶段约定；Linux 验证仍缺失，不能把可行性探针扩大为全部平台和版本的兼容承诺。

本设计不包含自动回滚、持久化断点续跑、集群调度、插件自动发现或完整产品安装配方。增加这些机制必须有真实消费需求，不能为可能的未来场景预建。
